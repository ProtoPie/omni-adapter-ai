# Server compatibility matrix

The adapter libraries target **Connect Omni** — the edition of the v2 platform that has
adapters (the cloud-integrated ProtoPie Connect edition has none). They do not speak the
legacy "ProtoPie Connect" (v1) wire and will not connect to it.

Languages: **TS** (TypeScript/JS) · **PY** (Python) · **C#** (.NET) ·
**KT** (Kotlin/JVM·Android) · **SW** (Swift) · **DA** (Dart/Flutter).

The adapter library degrades predictably on servers that predate a feature: unknown
`token/validate` body fields are stripped server-side, and `strictRouting`
silently falls back to plain broadcast. "Required server" below is the
server build that actually honors the feature. An **adapter-enabled server** (or web build)
is a Connect Omni build that ships the adapter features — adapter keys, declarations,
screens.

| adapter feature | TS | PY | C# | KT | SW | DA | Required server |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Join / send / receive / ack / reconnect | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | any Connect Omni server |
| History replay (`history(pattern?)`/`latest`, joined payload) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | any Connect Omni server. The snapshot is **state, not triggers**: on every (re)join whose joined payload carries it (the `stage:joined` fallback re-seeds nothing) it re-seeds `latest()`/`history()` and fires the `history` event (`HistoryReplaced` in C#/Kotlin, `.historyReplaced` in Swift), but it is never fed to channel handlers (all six) — a command published while an adapter was away is lost as a trigger and survives only as a last value. Deliberate: replaying into handlers would re-fire a stale `door.open` minutes late. It does mean trigger channels are at-most-once across a disconnect; state channels should read `latest()` on `connected`. `latest()` keeps the 1000 most recently updated channels (all six, `LATEST_LIMIT`; a stale out-of-order value does not refresh a channel) — before 2026-10-09 it grew with every distinct channel name |
| `members()` roster + presence events | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | any Connect Omni server |
| Credential policy — `cst_` envelope or bare `ck_` + `url`/`stageId`, nothing else (a share token is a `ConfigError` before any network call) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | any server that issues adapter keys |
| `cst_` token (programmatic encode) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | any (token is client-side encoding) |
| `cst_` token issued from the Share dialog (Adapter keys → Create key; the envelope's secret is a server-issued `ck_` key) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | adapter-enabled web build |
| **`ck_` adapter key** (server-issued, individually revocable) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | adapter-enabled server (created and revoked in **Share → Adapter keys**, Editors only). Unlike `cst_` it is **not self-describing**: pass `url` + `stageId` with it. In exchange it can be revoked or expired on its own — resetting the share token throws out every human participant too. On the wire it rides in the same `token` field; the server splits on the prefix, so older servers simply reject it as a bad share token (401). A locked stage (`allowAnonymousGuests: false`) blocks it like any other guest credential — an adapter is not a named human identity. **Join limits** (`token/validate`, per network address): share-link joins are limited to 5 a minute; a key join does not count toward that, but a failed key attempt does, and 20 failed attempts of either kind within 5 minutes refuse every join from that address — a correct key included — for the rest of the window. One key allows 60 joins a minute from any address — counted across the server instances on servers from 2026-10-19 (per instance before that, and on a deployment without Redis). Both refusals are `TooManyRequests` from `connect()`, never retried by the library. A server that cannot read the stored material of an older key on the stage (a key-encryption rotation left that key behind) answers `503 KeyMaterialUnavailable`; after 30 such answers to one address for one stage within a minute it stops checking keys from that address for that stage until the minute ends, so a correct key gets the same 503 — the fix is on the server side (revoke the old key, or restore its material). `connect()` reports it as `KeyMaterialUnavailable`; a joined adapter keeps retrying while it rejoins. Adapter-enabled builds before 2026-10-19 counted successful key joins too, so a sixth program joining from one address within a minute failed |
| Declarations (`receives`/`sends`/`osHostname`) → Backstage adapter node, `clientType: 'adapter'` stamp | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | adapter-enabled server (older servers strip the fields; connection still works) |
| Adapter identity on join (`adapter` · `adapterVersion` · `runtime` · `runtimeVersion` on every key join's `token/validate` — not an option) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | Servers from 2026-10-23 record it in their usage ledger (`adapter.joined{adapter, runtime}`, key joins only); older servers strip the fields — joining is unaffected. The fields carry **no user data**: the library's language, its own package version, the runtime family and the runtime's leading numeric version. Each library sends only values inside the server's vocabulary and patterns (servers from 2026-10-23 answered 400 to a value outside them; from 2026-10-25 the server drops just that field and admits the join) and omits a field it cannot derive — the browser's runtime version, a Python that is not CPython, a runtime version that does not start with a digit. Runtimes: TS `node`/`bun`/`deno`/`browser` · PY `cpython` · C# `dotnet` · KT `jvm`/`android` · SW `apple` (OS version) · DA `dart-vm`/`flutter-web` |
| `strictRouting` selective delivery (+ filtered history, unicast targeting) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | adapter-enabled server (older servers broadcast as before) |
| Offline queue · backoff · throttle · wildcard subscriptions | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | any Connect Omni server. Wildcards match by **segment DP, not a regex** — `listeners()` runs *other participants'* declared patterns (the server validates them only as 1..512-char strings), and the old `[^.]+(?:\.[^.]+)*` compilation backtracked exponentially on `*.*.*…` (measured 75 s of blocked CPU). **Client-side rate limit (all six, `message-rate` 60 / `message-burst` 30):** the server accepts at most 60 `stage:message` per second per socket (a token bucket, burst 60, counted at arrival) and silently drops fire-and-forget messages over it, so every publish — direct and queue flush — takes a token from a client bucket that refills 60 per second and holds at most 30 (lower than the server's burst because arrival clumps would otherwise overflow it; 30 absorbs about half a second). With no token a send goes to the queue; the bucket starts full on every (re)connect. Sustained sending above 60/s grows the queue until the oldest items drop (`QueueOverflow` per item, one `queue-overflow` ring entry per episode, re-armed once the queue has drained to half its limit) — the newest value still arrives instead of the server dropping random ones. A full default queue (1000) takes about 17 s to drain, which is also how far behind a ≥ 60/s sender can fall after a disconnect (lower `queueLimit` or throttle). The flush emits fire-and-forget items as tokens allow without awaiting their acks; an acked item waits for its server answer before the flush continues, so acked sends go one per round trip. A queued acked publish that comes back `AckTimeout` stays in the queue **and re-arms a short flush**: the socket is still connected, so no state event would ever wake it again. A `TooManyRequests` backoff requeues **silently** — no `send-dropped` entry — so recognise it as connected + `queuedCount` > 0 + not standby + no `send-dropped`. Only acked sends see a server rejection, and only they trigger the `TooManyRequests` backoff: a fire-and-forget send — direct or queued — asks for no ack, so it is at-most-once (a refusal, or a drop right after it went out, is never seen or retried). A queued acked send that already went out once before a drop and is later failed with `QueueOverflow`, `Standby` or `SessionEnded` may have reached the server too. `close()` drops queued fire-and-forget sends (queued acked ones reject with `SessionEnded`) — await an acked send or wait for `queuedCount == 0` first when the last values matter. A throttled `push(value)` checks the channel and value at the call site and throws `ValidationError` there, like `send` (a push after `close()` does not throw); delivery after a valid push stays fire-and-forget |
| **Messages actually firing a prototype's Receive trigger** | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | adapter-enabled web build |
| **Round-trip latency** (`ping()` + percentile summary) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | any — client-side only. Times a `stage:list-members` round trip: the one surface that has a request/response **and leaves nothing on the stage** (publishing to measure pollutes the Console and wakes the prototype's Receive trigger). It measures **adapter↔server**, not end-to-end to another participant — the server does not echo your own messages, so one participant cannot measure that at all. Failures are counted separately, never folded into the percentiles |
| **Repro bundle** (`buildReport()` / `Report.build`) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | any — client-side only. Still produced when the server is unreachable, which is exactly when it is needed most |

| `omni-adapter` CLI (`doctor [--json]`/`send`/`watch`/`latency`/`report`/`record`/`replay`/`simulate`) | ✅ | ✅ | — | — | — | — | any Connect Omni server. `doctor --json` prints the `CheckResult[]` (`{id, label, status, detail?, hint?}`) so a script can branch on a step instead of grepping prose; the exit code is the same in both modes (1 if any check failed). Since 2026-09-22 also `record` (watch → NDJSON file, append), `replay FILE [--speed X\|inf] [--loop N] [--ack]` and `simulate <channel> (--sine\|--ramp\|--random) MIN..MAX \| --step v1,v2,… [--hz N] [--count N \| --seconds S] [--period MS]` — the no-hardware verification loop from a shell. `replay`/`simulate` wait for the queue to drain (giving up after 15 s without progress) and exit 1 if anything is still queued, since `close()` drops queued fire-and-forget sends |
| Typed channels (per-channel payload types) | ✅ | — | — | — | — | — | TS generics only — `OnJson<T>`/`onJson` elsewhere deserialize, they don't type the channel map |
| React bindings | ✅ | — | — | — | — | — | same as the underlying feature |
| Clean shutdown on Ctrl+C / SIGTERM helper (`stop_on_signals`) | — | ✅ | — | — | — | — | any — client-side only. Python only: on 3.10 a Ctrl+C that reaches `asyncio.run` cancels every task before `finally` runs, so `close()` cannot send the leave, and Windows has no `loop.add_signal_handler`. The helper turns the first SIGINT/SIGTERM into a stop callback on the loop, lets a second one act as if no handler were installed, and restores the previous handlers on exit. | **Engine profile** (MessagePort, no credential/seat) | 🧪 | — | 🧪 | — | — | 🧪 | a host with the Engine port API **and** a layer that hands the page a MessagePort: a Connect Omni **Web View** layer (Add → Web View: the page URL — every Web View hands a port, no switch; one-step `adapter-view:init` handoff at the iframe load event carrying the layer's per-direction rules `receives` · `sends` plus their union `channels`) or an Engine definition declaring `stage-messaging` (dev builds ship the `dev-echo` probe definition). The Web View's **Stage messages** rules cap the page per direction: **Receive** caps subscribe, **Send** caps publish (up to 32 exact names each; empty = nothing passes) — `client.engine.allowedReceives` / `allowedSends` in TS, `allowedReceives` / `allowedSends` (Dart) · `AllowedReceives` / `AllowedSends` (C#) on `EngineTransport`; `allowedChannels` / `AllowedChannels` (the union) stays, deprecated. Hosts from before 2026-10-28 have an **Adapter View** layer instead (Add → Adapters → Adapter View: URL + one channel list) and send only `channels`, which the adapter applies to both directions. Call `connect()` during page start-up — the port is handed over once. Saving changed rules **closes the port** and a new one arrives only at the next iframe load (the host reloads the page), and the adapter ends the client (`ended`, reason `port-closed`) instead of hanging — TS watches the port's `close` event itself; C#/Dart bridges call `NotifyPortClosedAsync()` / `notifyPortClosed()` when they see it. ⚠️ The `MessagePort` `close` event is recent (Chrome/Edge 123, Firefox 123, Safari 17.4 — verify before relying on it): on an older WebView the adapter cannot see the close, so the page stays `connected` with every `send` ending in `AckTimeout` until it is reloaded. A `receives` entry outside the Receive rules is dropped by the host with no error, so compare your declaration against `allowedReceives` when a channel stays silent; a send outside the Send rules is refused (`denied`). `sends` is announced to the host (`engine:message-declare`) so Connect knows the page's channels before any message flows (Backstage chips for the channels the rules allow) — hosts from 2026-10-27, where a layer with empty rules still hands over a port that passes nothing (older hosts ignore the declaration and hand over no port until a channel is listed). From 2026-10-28 the page's subscription, its send declaration and any send the rules refused show up in the Web View's Stage messages as channels "This page asked for", only in the editor displaying the page; the designer adds them with **Add**. From 2026-11-05 the declared channels are turned on in the rules automatically when an editor's screen displays the page (a channel an editor turned off stays off); only what was not declared — a refused send, a wildcard, names past 32 — still waits for **Add**. `engine-channels` diagnostics are TS-only and compare each direction against its own rule. **TS · Dart (Flutter web) · C# (Blazor WASM)** — PY/KT/SW are marked — because there is no browser iframe runtime to host them, not because the work was skipped. In Dart and C# the adapter owns the *protocol* (two-step handshake, explicit subscribe, request/response correlation, state·lease·snapshot ops) and the app injects the parent-window bridge (`postMessage` + `MessagePort` transfer) — putting that dependency in the package would make the Dart package web-only and cost C# its netstandard2.0/Unity target. Only TS detects the profile on its own (a credential-less `connect()` in a framed page); in Dart and C# the app constructs an `EngineTransport` explicitly, and engine control (`allowedReceives` · `allowedSends`, state · lease · snapshot ops, port-close notice) lives on that transport, not on a `client.engine` property |
| `providesView` declaration (`none`/`web`/`stream`) → adapter is a screen candidate | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | adapter-enabled server (older servers strip the field; the adapter still connects, it just never appears as a candidate) |
| **Auto-rejoin on session resume** (`autoRejoin`, default on) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | any — it re-runs the normal join, so no new server surface. All six give up on the same five codes (`AuthRevoked`, version skew ×2, `ConfigError`, `ValidationError`) and keep waiting on everything else; C#/KT/SW only stopped on `AuthRevoked` before this revision. While waiting nothing is delivered live; on rejoin the history snapshot re-seeds state but does **not** re-fire handlers (see History replay). A **server-side disconnect** (the server cuts an adapter whose key was revoked or expired) takes the same path in all six — revalidate, then `rejoin-abandoned: AuthRevoked` for a dead key (`server-disconnect` with `autoRejoin` off); a terminal rejection after the join ends the client with `rejoin-abandoned: <code>`, and a token that cannot be renewed ends `reauth-failed` with `autoRejoin` off (2026-10-03 — before it, TS stayed `reconnecting` forever and queued ack sends could hang) |
| `retryAfterMs` on join refusals (`connect()` 429 `TooManyRequests` · 503 `KeyMaterialUnavailable` carry `AdapterError.retryAfterMs`; the rejoin waits at least that long) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | every adapter-enabled server sends `details.retryAfterMs` on the 429 (the address failure cap: the rest of its 5-minute window, ≤ 300 s; the per-minute gate; from 2026-10-19 also the per-key limit's remaining minute, and 1 s when more than 200 joins are being validated at once); the 503's `retryAfterMs` comes with servers from 2026-10-19. There is no `Retry-After` header. The adapter caps the value at 10 minutes; when it is absent the usual 2 s → 60 s backoff applies. Servers from 2026-10-19 classify a `ck_` token as an adapter key only when it is 46 characters long — a 401 for a key of another length gets a "truncated or altered key" hint instead of "revoked" (message and `doctor` say the length). 503 `KeyMaterialUnavailable`: the server cannot read the stage's adapter-key material (an older key left behind by a key change). | `exclusiveName` declaration (one active per name) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | adapter-enabled server (older servers strip it; instances stay independent) |
| **Standby behaviour** (stop sending / keep receiving / resume on promotion) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | same server. **All six now suppress automatically** — the roster's `standby` is the server's judgment and the adapter never re-derives it. Every send path is gated, including the offline queue (gating only the direct path lets a reconnect flush double-publish), and an `ack: true` send **rejects** with `Standby` rather than resolving. Each (re)connect resolves standby **before** flushing: `stage:joined` carries no `standby` (it comes from the runtime map, not the roster) and your own rejoin raises no presence event for you, so an adapter that rejoined into a standby slot would otherwise never find out. While standby, new sends are dropped (fire-and-forget, debug log only, no ring entry) or rejected with `Standby` (acked) — never deferred, even with a non-empty queue. When an instance **becomes** standby by any path (a reconnect judgment or a presence change), everything it has queued is dropped too: fire-and-forget discarded (the `standby` ring entry ends with `— dropped N queued sends`), acked items rejected with `Standby`; an item already emitted and waiting for its answer is left to that answer, and one whose answer is `AckTimeout`/`TooManyRequests` while standby is rejected with `Standby` instead of requeued. Another instance has been the active producer meanwhile, so flushing old values on a later promotion would revert newer state — on promotion nothing stale goes out. With `exclusiveName`, each (re)connect needs one roster round trip to judge standby before the queue flushes; sends made during that window are held aside (sharing `queueLimit`) and, once judged, join the end of the queue (active) or follow the standby rule; a failed judgment counts as active, and presence changes during a pending judgment coalesce into one more judgment after it. There is no standby-change event: read `standby` (per-language case) or the ring's `standby`/`active` entries |

| Roster carries adapter declarations (`members()` → `receives` · `sends` · `clientType` · the strict-delivery flag · `exclusiveName` · `osHostname`, plus `declaresChannel(channel)`) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | same server (every field is already on the wire as `StageMember`; older servers omit them → absent, never defaulted). Absent `receives` means **undeclared**, i.e. a broadcast receiver (browsers and prototypes never declare) — `declaresChannel()` is false for them, so "nobody listens to X" needs *no declared match* **and** *no undeclared member* — `listeners(channel)` (next row) does that split for you |
| Listener lookup (`listeners(channel)` → `declared` · `broadcast`, self excluded) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | any — client-side over one `stage:list-members` round trip. `declared` = members whose `receives` matches (exact or wildcard); `broadcast` = members that receive it anyway (no declaration, or declared other channels without strict delivery); a member that declared other channels **with** strict delivery is in neither — it will not get it. Not wired into `send()` on purpose — a round trip per publish would add latency; call it once before wiring, or from a diagnostics screen (the ring entry is recorded once per channel and re-armed when a declarer appears, so polling does not flood it). Pass a **concrete** channel — patterns are not expanded. On the Engine profile there is no presence round trip: both lists come back empty and nothing is recorded |
| In-memory stage (test harness: `MemoryStage` → `join()` · `inject()` · `disconnect()`/`reconnect()` · `end()` · `rejectPublish`) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | none — no server, no credential. | Playback helpers (`replay(client, recording)` · `simulate(client, channel, waveform)` · `parseRecording`/`formatRecorded`) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | none — client-side, publishes through `send()` so queue/standby/backoff rules apply unchanged. Recording format is `watch`'s NDJSON (`{ts, channel, value, from}` per line); `replay` keeps the recorded gaps (÷ `speed`, `Infinity` = no gaps), `simulate` emits sine · ramp · random · step at `hz`. | **Screen broadcast helper** (announce · answer · ICE · cleanup) | 🧪 | 🧪 | 🧪 | 🧪 | 🧪 | 🧪 | adapter-enabled web build (needs the **Adapter Stream** layer). **All six now ship the helper**, and none of them gained a dependency: the helper owns the *protocol* and you inject one session per viewer (browser `RTCPeerConnection`, `aiortc` via Python's `[stream]` extra, Unity.WebRTC, `flutter_webrtc` in your app — never in the package, which is what keeps `flutter build web` working). Two rules it encodes because both fail *silently*: announce `{"kind":"ready"}` on **every** connect (a reconnect included — subscribe to state *transitions*, not the current-state value, or a fast reconnect collapses into no re-announce), and attach the track to a stream so the answer carries `msid`. Cleanup (all six, 2026-10-03): after a reconnect the helper closes viewers missing from the server's `peers` reply to its `ready` (a `peer-left` sent while the adapter was away is otherwise lost), keeps one generation per offer so an outdated answer attempt never touches the current session, and stops itself when the client ends. Sessions are keyed by (participant, `receiverId`) (all six): the web tags offers and ICE with a `receiverId` per receiver, so two tabs of one PIN guest no longer close each other's connection; a new offer replaces only that receiver's session, `peer-left` and the `peers` reconciliation close every session of the participant, answers and ICE echo `negotiationId` and `receiverId`, and a viewer without `receiverId` (older web) keeps one session per participant. The web keeps one receiver per (viewer page × adapter participant), not per layer instance. A participant keeps at most 4 receiver sessions. A fifth evicts first a session the helper knows is not live (TypeScript: its connection is not `connected`; where the app injects sessions: a receiver whose session has not sent its answer yet — an answered session stays live while it renegotiates), then the least recently negotiated one. Until a vanished tab is noticed — ICE takes seconds to report it, and an injected session only once the app passes it to `session_closed`/`sessionClosed` — a live tab that never renegotiates can be the one evicted, so report closures. Only PIN and share-link guests keep their participant id across a refresh and so leave old receivers behind; team members get a new id per socket and leave with `peer-left`. When the adapter becomes connected with a new participant id (a rejoin into a new session, the 6-hour guest-token revalidation), the sessions from before the drop are closed (measured before the fix: 5 rejoins → 5 dead peers); sessions opened to the new id while it was still reconnecting stay. Early viewer ICE is queued per receiver and applied once the offer is set (a real-browser run lost 36–50 of ~105 candidates per session before; with 250 ms of adapter latency every viewer waited ~20.8 s): the current attempt's candidates wait with no age limit; candidates that arrive before the offer wait up to 10 s, matched by `negotiationId`, with at most 4 waiting receivers per viewer and 64 in all; at most 200 per receiver; every forget path clears them. The ICE-server lookup times out after 5 s and answers with the last known servers (else STUN, else none), noting `ice-servers` once; a failed lookup is never cached (before, one transient failure left the client host-only, or STUN-only after a 5xx on the stage route, for its lifetime). ## Protocol gates

Every connection stamps `PROTOCOL_VERSION` (`0.1.0`). The server enforces
same-MAJOR interop (all 0.x interoperate) and, once activated after the 1.0
wire break, a minimum client floor — both rejections are terminal and the
adapter surfaces the exact required version in the error message.

One gate lives outside the protocol version: the server's `token/validate`
`clientType` is a closed enum (`'adapter'`). A pre-release adapter build that
still self-reported the old value is rejected with **400 ValidationError** on
every connect — not `ProtocolVersionMismatch` — so update the adapter rather
than the server when you see that error against a current server.

`token/validate` failures are classified from the server's error envelope
(`{ error, message?, details? }` — the code is in `error`). All six adapters
share one mapping: 401/403 → `AuthRevoked` (a `ck_` key gets an "issue a new
adapter key" hint, `stage-locked` asks the stage owner or whoever runs the Connect to reopen it to guests — `allowAnonymousGuests` has no switch in the web app), 404 →
`RoomEnded` (a `ck_` key is pointed at a key created with "Let adapters start a session") or
`StageArchived`, 409 `StageFull` surfaces as `StageFull`, 429 → `TooManyRequests` and 503
`KeyMaterialUnavailable` → `KeyMaterialUnavailable` (both carry `retryAfterMs` when the server
sends `details.retryAfterMs`; any other 5xx passes the envelope code through without a hint).

**Prototype → adapter delivery.** From 2026-10-19 the server rewrites the
channel of `STUDIO`-scoped messages (prototypes, Figma and Unity layers, the Console) to the message
name for adapter sockets only, so `on(name)` fires and a `strictRouting` adapter receives them by
declaring the name. Older servers deliver them on channel `STUDIO` with the name in `messageId` — a
name subscription never fires there. The adapters apply no client-side rewrite; `messageId` is still
carried on every message.

## Known honest limits (all servers)

- A stage session belongs to the person who created the stage — adapters join as guests
  and start one only with a key created with "Let adapters start a session" turned on (Share →
  Adapter keys — a key keeps the setting it was issued with; servers before the per-key change had one switch per stage). Each External-profile connection consumes one guest seat.
- History is a replay ring (≤1000 messages), not persistent storage.
- Binary payloads are not supported; values are primitives with a
  JSON-string convention for structured data.
- Standby suppression: the server's judgment is on the roster in **all six**
  languages (`Member.standby`), and **all six now act on it automatically** (stop
  publishing while standby, resume on promotion, record the reason). The rule is
  the server's — never re-derive it client-side, and treat an absent `standby` as
  *active*, not standby (older servers omit the field entirely).
- Engine profile v1: no ring-buffer history replay (but `latest()` is seeded — the host replays each subscribed channel's most recent value), no `sendTo()`; `members()` answers with
  an empty roster rather than throwing.
- Ack timeouts are enforced by the adapter library in C#/Kotlin/Swift: C# and Kotlin wrap
  the emit themselves (their libraries have no ack timeout), and Swift uses the
  library's `timingOut(after:)` **plus** its own fallback — the library's
  timeout holds only a weak socket reference, so it never fires once the socket
  is released. All surface `AckTimeout` exactly like the other adapters.
- History is a replay ring whose size is a server setting
  (default 1000) — "≤1000" above is that default,
  not a hard protocol cap.

## Known small differences between the six languages

Shared test vectors make `parseStageToken`, `parseRecording` and `matchChannel` give the
same accept/reject decision, error code and value in all six languages. These differences
are left as is:

- **The sign of zero in recordings.** `-0` reads as `-0` in TypeScript, as `+0` in
  Python, Kotlin and Dart, and C# keeps it for `ts` but not for `value`. On the wire it
  makes no difference (`JSON.stringify(-0)` is `0`).
- **Integers above 2^53 in recordings.** TypeScript and Swift read them as doubles;
  Python, C# (`Int64`), Kotlin (`Long`) and Dart on the VM keep the exact integer up to
  their integer range. Peers receive the same double after the server relays it, but
  `RecordedMessage.value` and what `replay()` publishes differ in the last digits.
- **The value shown in `unsupported stage token version (…)`** is each platform's own
  rendering (`undefined` / `None` / `?` / `null`, `true` / `True`, …). The message is
  not part of the contract; the error code is.
- **C# on .NET Framework or Mono** (the netstandard2.0 build, e.g. Unity): number
  parsing goes through that runtime's `double.TryParse`, which may round numbers with
  hundreds of significant digits differently from IEEE. .NET 8 is what CI measures.
